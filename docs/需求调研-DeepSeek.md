# AI 小说生成项目 · 全网调研与提示词体系设计任务书 v2.1

## 0. 任务总览

你是本任务的主控 Agent。你的任务不是直接回答“AI 小说项目该怎么做”，而是分两个阶段完成：

**阶段一 · 调研**：自主制定调研计划，派发子代理，联网搜索全网与 GitHub，回收并交叉验证，产出一份带 URL 的调研报告。

**阶段二 · 设计**：基于调研结果，产出一套可直接用于项目的完整交付物——功能架构清单、流程设计、以及覆盖所有模块的提示词体系。

最终交付物是“设计方案 + 提示词体系”，调研报告是中间产物。

你必须实际执行联网搜索，禁止凭训练数据作答。所有关键结论必须附可访问 URL。**禁止编造项目名、仓库名、功能或数字**；搜索不到的内容写“公开资料有限”，不得用看似合理的名字填充。

本项目最终以代码形式接入 LLM 运行，因此本次任务只产出调研报告与设计交付物，不涉及平台适配、工具选型或多端部署方案。

---

## 1. 用户需求原文（设计阶段的验收依据）

用户要做一款 AI 长篇小说生成项目，需要调研并设计以下内容（原文归纳）：

1. 项目需要具备哪些功能
2. 提示词应该如何写
3. 流程如何设定
4. 大纲、细纲、骨架、背景、设定、世界观、武力等级等怎么设计
5. 全网和 GitHub 都要查找
6. 用户没提到但项目需要的内容要补全
7. 最终要一份“最全面的提示词”，涵盖所有方向

设计阶段的交付物必须逐条对应以上 7 点，缺一不可。

## 2. 阶段一 · 调研

### 2.1 自主规划（先输出，后执行）

先输出一份调研计划，包含：

- 调研方向清单（建议六个，可增删，但必须覆盖用户第 1 节的全部 7 点）
- 每个方向的搜索关键词矩阵（中英文各 4—6 组）
- 优先级信源清单（10—15 个 URL，说明每个预期提供什么）
- 派发计划（哪些方向并行、哪些串行）

**建议的六个调研方向**（你应根据实际搜索情况调整，不要机械照搬）：

- 方向 A：现有 AI 小说生成开源项目的功能架构与工程机制
- 方向 B：小说生成提示词模板的结构模式（世界观、角色卡、大纲、细纲、正文、审校、去 AI 味）
- 方向 C：长篇分层规划流程（骨架/大纲/细纲/章节合同的层级与滚动冻结）
- 方向 D：长程记忆、状态台账、伏笔管理与一致性校验
- 方向 E：调研型 Agent 提示词的可迁移结构（DeepResearch 类）
- 方向 F：写作技法层面的设计法（力量体系、角色弧光、类型专项）

**搜索关键词原则**：用能力描述词，不要用具体项目名。例如用 “AI novel generator multi-agent github” 而不是某个仓库名；用 “小说生成 伏笔 台账 一致性” 而不是某个具体项目名。具体项目名应由搜索结果自然浮现，不得预先写入查询词。

### 2.2 派发子代理

为每个调研方向派发一个子代理。每个子代理的任务书必须包含四部分：

**（1）必答问题清单**：该方向必须回答的具体问题，问题要落到“机制如何实现”而不是“有没有”。

**（2）搜索策略**：中英文查询词各 4—6 组；优先打开 GitHub README/docs、技术博客、提示词仓库；中文社区内容仅作线索，结论需 A/B 级来源佐证。

**（3）输出 schema**：每个发现一条，包含“结论 / 原文摘录≤80字 / URL / 信源等级 A/B/C / 置信度 高/中/低”；末尾必须有“横向归纳”和“资料缺口”两节。

**（4）质量门**：最少来源数、必须引用的原文数、禁止编造的声明。

**六个子代理的必答问题（直接派发时使用）**：

子代理 A · 开源项目架构
- 规划层级是几层？每层产出物是什么？
- 是否有结构化台账（角色状态、物品资源、伏笔、时间线、关系）？如何更新、如何注入下一章？
- 一致性校验有无代码层机械检查与 LLM 审校？各覆盖哪些项？
- 是否多 Agent 分工？边界如何划分？
- 是否支持 checkpoint、断点恢复、正文版本绑定？
- 项目 README 中写明的“已实现规模”（已生成多少章/多少字）是什么？这比功能列表更有参考价值。
- 质量门：≥5 个项目、每个有可访问 URL、至少 3 个引用 README 原文、无编造项目名。

子代理 B · 提示词模板结构模式
- 世界观设定提示词是否强制“规则—代价—限制—例外”结构？力量体系是否要求等级、克制、越级代价？
- 角色卡是否包含“表面目标/深层渴望/恐惧/弱点/关系冲突”？是否要求矛盾面？
- 大纲/细纲提示词的字段通常有哪些（核心事件、情绪走向、冲突类型、伏笔操作、钩子类型、字数区间）？
- 单章正文提示词如何注入设定与状态？是否区分“必须完成事件”与“禁止超出范围”？
- 审校提示词是否要求“引用原文举证”？审校项如何分类？
- 去 AI 味提示词是否先写后检？检测哪些具体模式（排比三件套、名词化动词、抽象主语、金句收尾等）？
- 质量门：六类模板全覆盖，每类 ≥1 个可验证来源；结构骨架用抽象字段名表达，不大段复制原文。

子代理 C · 分层规划流程
- 各项目把“骨架”“细纲”叫什么？每层覆盖多大范围（全书/卷/弧/3章/单章）？
- 是否存在“章节合同”或等价物？合同字段有哪些？何时冻结、冻结后能否修改？
- 后续弧/卷的大纲在什么时机展开？依据什么信息展开？
- 流程中哪些节点设人工确认，哪些全自动？
- 有无项目明确处理“大纲与正文逐渐不一致”？用什么机制？
- 质量门：≥4 个项目/方案进入对比表；“骨架 vs 细纲”的专论必须有来源支撑。

子代理 D · 记忆与一致性
- 台账种类：角色状态/物品资源/伏笔/时间线/关系图谱，哪些项目实现了？数据结构大概什么样？
- 状态注入是“全书前文”还是“最小相关上下文”？如何判定相关性？
- 哪些检查用代码规则（零 token），哪些必须 LLM？分工边界在哪？
- 伏笔管理有无伏笔池、是否分级、有无超期预警、是否禁止同章立即回收？
- 返工后如何保证审校对象即最终版本？有无 digest/hash 绑定？
- 质量门：五类机制全覆盖；“优先实现建议”必须基于 ≥2 个来源的收敛证据，不得主观排序。

子代理 E · 调研型 Agent 提示词
- DeepResearch 类 Lead Agent 提示词如何拆解任务、分类查询类型、管理子代理？包含哪些结构块？
- 调研型 Agent 如何生成搜索词变体？有无“主词+详解+权威限定”策略？
- 是否区分“已确认事实/估算/推断”？是否强制每条结论附 URL 与原文摘录？
- 小说调研的特殊性：时代细节、职业细节、地理细节、战斗合理性、同类作品写法参考——如何转成搜索策略？
- 调研结果以什么格式交付写作流程（Markdown 参考文件/事实清单/对比表/摘要包）？
- 质量门：可迁移结构每条有来源；输出模板必须是字段级结构。

子代理 F · 写作技法与类型专项
- 世界观硬规则如何“约束剧情而非装饰氛围”？“能力—代价—限制—例外”的来源与实践案例？
- 力量/武力体系：等级、克制、越级代价、以弱胜强的结构性通道如何设计？战力崩坏的典型成因？
- 角色卡的目标—恐惧—弱点—关系冲突框架（want/need/ghost、角色弧光）如何落到字段？
- 三幕/救猫咪/故事圈等结构法如何与章级细纲字段对应？情绪走向与钩子类型有哪些分类法？
- 中文网文语境下“AI 味”的具体表现清单与改写手法，有无实证或社区共识来源？
- 至少覆盖玄幻/仙侠（力量体系）、悬疑（伏笔与信息差）、都市/言情（关系张力）三类类型，各给出该类型特有的设定字段。
- 质量门：六项全覆盖；每个方法必须给出可命名的提示词字段名；类型至少三类。

### 2.3 回收、校验与仲裁

- 按 schema 回收，不符合的退回重做。
- 抽查每个子代理 20% 的 URL，确认可访问且内容匹配；死链或内容不符的条目退回。
- 跨方向去重：同一机制被多项目采用时合并为一条并列出多个来源。
- 冲突不强行归一：两个来源定义不一致时并列保留并标注来源。
- 每方向 A/B 级来源少于 3 个时，在报告中单列“资料缺口”。

### 2.4 调研报告结构

- 调研方法与信源概况
- 开源项目机制横向对比表（项目 | 规划层级 | 台账 | 校验 | 多 Agent | 可借鉴细节 | URL）
- 六类提示词模板的字段收敛与结构骨架
- 分层规划的共识与分歧
- 长程一致性机制的优先级（标注证据数）
- 调研型 Agent 的可迁移结构
- 写作技法到提示词字段的映射表
- 资料缺口
- 来源索引

## 3. 阶段二 · 设计（最终交付物）

基于调研报告，产出以下五份交付物。这是用户真正要的东西，调研只是手段。

### 交付物 1 · 项目功能架构清单

按模块列出项目应具备的功能，每个模块写清“解决什么问题 / 核心机制 / 与哪些模块交互”。必须覆盖：

- 分层设定库（世界硬规则、力量体系、势力地理、角色档案、资源账本）
- 滚动规划引擎（书→弧→章，骨架与细纲的边界，冻结时机）
- 长程记忆与状态台账（角色状态、物品、伏笔池、章节事实摘要、注入策略）
- 文风引擎与去 AI 味（文风蒸馏、后处理检测）
- 审校—返工闭环（代码层机械检查 + LLM 层语义审校 + 定向修复）
- 人机协作关口（试写确认、弧纲确认、运行中注入、断点恢复）
- 调研 Agent（考据、参考分析、事实清单产出）

### 交付物 2 · 流程设计

写清三阶段流程，每个阶段标注输入、输出、人工关口、冻结对象：

- 阶段 0：书级立项（方向候选 → 试写 → 锁定）
- 阶段 1：书级设定与前 1—2 弧骨架
- 阶段 2：弧级冻结与章纲合同展开
- 阶段 3：单章闭环（章纲加载 → 状态注入 → 正文 → 机械检查 → LLM 审校 → 定向修复 → 事实提取 → 台账更新）
- 阶段 4：弧末回顾与滚动刷新

每个阶段必须回答：产出物是什么、什么被冻结、下一阶段依赖什么。

### 交付物 3 · 完整提示词体系（核心交付物）

这是用户第 7 点“最全面的提示词”的直接对应。每个模块给一份可直接使用的提示词模板，变量用〖〗标注。必须包含：

- P1 书级方向生成提示词
- P2 世界观硬规则与力量体系提示词（强制“能力—代价—限制—例外”结构）
- P3 角色卡提示词（强制“表面目标/深层渴望/恐惧/弱点/关系性冲突”）
- P4 骨架与弧纲提示词
- P5 细纲/章节合同提示词（字段：章号、必须完成事件、情绪走向、冲突类型、伏笔操作、钩子类型、字数区间、POV 知识边界）
- P6 单章正文生成提示词（注入合同、状态快照、前情锚点、文风指令、写作约束优先级）
- P7 代码层机械检查规则清单（零 token，逐条可执行）
- P8 LLM 层一致性审校提示词（逐项“通过/冲突”，冲突引用原文举证）
- P9 去 AI 味后处理提示词（先写后检，列出具体命中模式与改写约束）
- P10 调研 Agent 提示词（用于小说考据与参考分析，含搜索策略与输出模板）

每份提示词模板必须包含：角色定位、输入变量、输出结构、硬约束、禁止项。不允许只给“请写一个世界观”这种空泛指令。

### 交付物 4 · 各模块设计要点说明

逐条回答用户第 4 点的每个词，说明“怎么设计”以及“如何转成提示词约束”：

- 大纲：解决什么、不该承载什么、与细纲的边界
- 细纲：字段设计、验收标准、与章节合同的关系
- 骨架：书级骨架与弧级骨架的区别、滚动展开时机
- 背景：如何拆成“可被角色触碰的规则”与“可被剧情揭示的历史”
- 设定：设定库的组织方式、版本绑定、注入策略
- 世界观：硬规则写法、禁忌与代价、避免说明文倾泻
- 武力等级：等级划分、克制关系、越级代价、以弱胜强的结构性通道、战力崩坏的预防

### 交付物 5 · 补全清单

列出用户没提到但项目必须有的模块，每个说明“为什么需要 / 不做的后果 / 最小实现方案”。至少覆盖：

- 长程记忆与状态台账
- 伏笔池分级与超期预警
- 代码层机械校验（零 token）
- 返工版本绑定（digest/hash）
- 断点恢复与 checkpoint
- 人机协作关口
- 去 AI 味后处理
- 调研 Agent（考据与参考分析）
- 文风蒸馏与风格一致性审校
- 章节事实提取与台账回灌

## 4. 执行约束（全程生效）

1. 禁止凭记忆作答；每个关键结论附可访问 URL；无法验证的标“未验证”。
2. 禁止编造项目名、仓库名、功能、章节数、数字；搜索不足写“公开资料有限”。
3. 信源分级：A 级 = GitHub README/docs/官方文档/论文；B 级 = 技术博客/出版写作书/编辑长文；C 级 = 社区帖/自媒体（仅作线索）。
4. 中英文查询并用；中文覆盖网文实践，英文覆盖工程与写作技法经典。
5. 明确区分“多项目收敛（刚需）”与“单项目设计（参考）”。
6. 每个子代理末尾必须输出“资料缺口”清单。
7. 设计阶段的每份提示词模板必须可独立使用，不依赖未给出的上下文。
