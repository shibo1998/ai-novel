`frontend/tailwind.config.ts:4`、`frontend/src/index.css:10`：暖墨黑底、朱砂主强调、暖金辅助、米白稿纸，阅读字体与控件字体分开；`AppShell.tsx:40`把项目总览、创作设定、生产控制台分成清楚导航，侧栏展示当前项目。

## 4. 与当前项目的差异

当前 `web/src/views/PlanningView.vue:76`直接暴露全书→卷→单元→章纲批次树；221、252、277分别要求候选生成、预览、采纳，采纳还有二次确认。`web/src/utils/planning.ts:39`默认下一批至多10章、不跨单元，因此并非没有批量章纲能力，主要负担是内部层级与确认步骤都变成作者操作。

现有规格08确实约定逐层采纳，不能把合并点击伪装成不变的纯样式改动；调整为卷级联合候选/采纳需要明确增补契约。但**规划层确认合并**与**单章细纲确认/定稿自动化**不同，后者仍不可绕过。

## 5. 推荐的最小方向（尚未批准实施）

1. **卷工作台为默认入口**：显示本卷目标、章数、章纲/正文进度与章节列表；剧情单元和内部层级放进高级详情。
2. **生成本卷规划**：用户给本卷目标和期望章数，后台分阶段生成必要的卷/单元/章纲候选，前台只看一个任务进度及一份联合影响预览，作者一次明确采纳。不是偷偷自动确认原有层级。
3. **本卷追加N章 / 新增下一卷**：追加未来章纲，起始章号服务端确定；明确是否需要延长当前卷或开启新卷，避免静默改卷末目标。不覆盖已确认细纲/已写正文、不重编号。
4. **单章创作入口收口**：从章节列表进入写作；保留细纲确认与定稿两个作者决定，显示检查和失败后的下一步，不让用户手动调度每个底层阶段。
5. **独立视觉系统**：借暖墨/朱砂/稿纸和主次按钮层级，先围绕卷工作台和写作页做，不一口气重构所有页面。

不照搬参考项目初始/重新生成时清除旧Chapter/Scene/Volume的实现（`outline_planner.py:351`），也不照搬生成即落库的语义；保留本项目文件真相源、增量保护、候选预览和人工关。

## 6. 下一步只需确认的分歧

用户希望“一次生成一卷”究竟是：

- 本卷全部**章纲/章节目录**先批量准备好（推荐先做），正文仍在人工确认后生成；
- 还是希望**正文**也由一个卷级任务连续生成（必须另定细纲确认、定稿和队列遇阻停止策略）。

UI与操作可先明确成卷工作台；不因用户表达更省事，就移除既有人工红线或自动调用真实模型。确认目标后再出小规格/原型，不直接实施本报告中的建议。
