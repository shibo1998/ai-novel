# 开发流程（WORKFLOW）

> 定位：规定**一次改动从想法到收口走哪几步、每步的产物是什么、什么时候必须停下来问人**。
> 权威关系：`docs/specs/` 是需求真相源，本文只管流程。两者冲突时规格优先，并回来改本文。
> 配套模板：`docs/templates/规格模板.md`、`docs/templates/验收报告模板.md`。

## 0. 一句话

**先分档 → 该拷问的才拷问 → 规格写清「不做什么」和「怎么算过」→ 改前记基线 → 分阶段实现 → 按影响面复测 → 回写 + 收口。**

---

## 1. 第 0 步：分档（每次改动的第一个动作，不许跳过）

问三个问题：

1. 会不会动到 `ainovel/api.py` 接口契约、`books/` 文件格式、SQLite 表结构、章节状态机、提示词契约、或 §6 的红线？
2. 会不会影响一个以上模块，或前后端都要动？
3. 你作为用户能不能看出行为变化，且这个变化是"新能力"而非"修错"？

任一为"是"→ **L2**；只在一个模块内、不动契约、是修正既有行为 → **L1**；单点错误修正 → **L0**。

| 档 | 判据 | 入口 | 产物 | 复测 |
|---|---|---|---|---|
| **L0 修补** | 单点 bug / 文案 / 样式，不动契约 | 直接定位根因（**不用 grill-me**） | 一处 diff | 相关测试 + 手验那一条 |
| **L1 单点功能** | 一个模块内，不动契约 | 轻量拷问 3–5 问（可自己问） | 现有规格增补一节，或 `docs/审查修复批次.md` 登记一行 | 离线全量 + smoke + 前端三步（若动前端） |
| **L2 跨模块** | 动契约 / 状态机 / 格式 / 提示词 / 红线 | grill-me 多轮 + 方案拷问 | 独立规格 `docs/specs/NN-xxx.md` + 批准快照 | L1 全部 + 真实书副本回归 + **1 章真模型对比** |

### 分错的代价（必须知道，不是形式主义）

- **L2 当 L1 做**：规格没写、边界没划，实现时顺手改到别处；事后几份规格互相打架，下次 AI 读到的是错的上下文。
- **L0 当 L2 做**：一个错别字走三轮拷问加一份规格，节奏被拖死，于是你开始"这次先跳过流程"，流程等于没有。
- **L1 当 L0 做**：以为只是改一行，实际牵出连锁反应，复测只跑了相关文件，坏掉的地方没验。

---

## 2. L0 修补

步骤：**说清根因 → 一处 diff → 定向复测 → 提交。**

要求：

1. 必须先说清根因（哪个函数、哪一行、什么条件下错）。说不清就是 L1，别硬当 L0。
2. 不许"顺手"改邻近代码。改到 README 偏差所列的有意行为时，保持原样并同步偏差记录。
3. 定向复测：`python -m pytest tests/<相关文件> -q` + 手验那一条现象。
4. 若根因是**某检查器静默失效 / 校验被绕过 / 接口 200 但没写档**，必须补一条能复现的测试。这是最该补测试的场景，别只改不测。

---

## 3. L1 单点功能

**3.1 轻量拷问（3–5 问，不需要 grill-me）**

- 用户可见的问题是什么？现在什么表现？
- 改动落在哪个模块、哪个函数？
- **明确不做什么？**（必答，写进产物）
- 怎么算做完？给一条可观察的判据，不用形容词。
- 会不会碰到 §6 卡点？

**3.2 规格**：不新建文档。写进对应规格的增补章节，或在 `docs/审查修复批次.md` 按现有格式登记（编号 + 现象 + 判据 + 涉及文件）。

**3.3 实现**：一次只做一件事，一个功能一个 commit。

**3.4 复测**：见 §5.2。

---

## 4. L2 跨模块

**4.1 喂上下文（grill-me 之前必做）**

grill-me 什么都不读就开始问，会把规格里早答过的问题重问一遍，你会在第三轮失去耐心然后草草批准。开工前固定喂：

- `AGENTS.md`
- 相关规格全文（`docs/specs/`）
- `.workbuddy/memory/` 最近三天日志 + `MEMORY.md`
- 目标模块源码
- `docs/功能蓝图与差距.md` 里对应条目

**4.2 grill-me 拷问需求层**：只问"要什么 / 不要什么 / 边界 / 优先级 / 失败时怎么办"，**不问实现细节**（实现细节下一轮问）。

停止条件（三条全满足即停，别无限追问）：
1. 能写出可判定的验收判据；
2. 能写出不做清单；
3. 所有分歧都有结论（有结论 ≠ 有共识，有分歧就记"取 A，理由是…"）。

**4.3 方案拷问（用 Plan 模式，不用 grill-me）**：改动面清单、数据迁移、失败模式、回滚方式、会打破哪些现有测试。

**4.4 出规格**：按 `docs/templates/规格模板.md`。强制项：§0.2 不做清单、§6 可判定的验收判据、§7 授权边界、§8 回写清单。四节留空视为规格不合格。

**4.5 批准**：你点头后才动代码。批准快照落 `.pi/plan/`（沿用规格06 的做法），规格头写清版本与实现基线 commit。

**4.6 分阶段实现**：每阶段结束跑一次测试并比 FAILED 集合（§5.0）。不允许全部写完再一次性测——那样失败时定位不到阶段。

**4.7 复测**：见 §5.3。

**4.8 出验收报告**：按 `docs/templates/验收报告模板.md`。**不得用修改规格来替代实施记录。**

**4.9 回写 + 收口**：见 §7。

## 5. 复测清单

### 5.0 通用纪律（四条，违反其一即复测无效）

**(1) 先记基线，再改代码。**

```bash
python -m pytest tests/ -q > /tmp/ainovel-before.log 2>&1 || true
grep '^FAILED' /tmp/ainovel-before.log | sort > /tmp/ainovel-before-failed.txt
wc -l < /tmp/ainovel-before-failed.txt
```

改完同样生成 `ainovel-after-failed.txt`，`diff` 两份。**判据只看 FAILED 集合的差**，不看总数、不看退出码。

**(2) 退出码不可信。** 本机 pytest 退出码恒为 1，是 safe-delete 护栏拦住 tmpdir 清理（日志里出现 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]`）。看到这个字样就是护栏，不是测试失败。同理，`--basetemp` **不要**指向项目内路径，否则 tmpdir 落进仓库、清理被拦，会造出一批假失败。

**(3) 假绿检查。** 接口 200、测试通过都不代表文件真写了。涉及写档的改动，复测必须打开生成的文件看内容，或断言内容指纹变了。这条是这个仓库的 F-01，别在复测环节又栽一次。

**(4) 不碰真实数据。** 不运行 `run.py`（它读写真实 `books/`、`data/` 并开浏览器）；不在测试里读写真实目录。确需真实书验证时，走 §5.3 第 6 条的副本方式。

### 5.1 L0

相关测试文件 + 手验现象消失。

### 5.2 L1

1. §5.0 基线 diff
2. `python scripts/smoke.py`
3. 动前端：`npm run lint:check` → `npm run typecheck` → `npm run build`（三步全过才算完）
4. 动提示词：`python -m pytest tests/test_prompts.py -q`，确认 `version` 已递增、渲染无残留 `〖〗`
5. 动档案/索引：§5.3 第 6 条（真实书副本回归）

### 5.3 L2

L1 全部，加：

**6. 真实书副本回归（必做）**

目的：挡住"单测全绿、真实书一个字都存不进去"。这个坑踩过——给 Bible 表头加严格全等校验，真实书里 `隐藏等级(低/中/高)` 被判成缺列，整本 STORY_BIBLE 任何一节都存不进。

做法：临时 home 里放 prompts / lint / 一本真实书的副本，`AINOVEL_HOME` 指向它，跑 rebuild + 全章机检。

```bash
TMP=$(mktemp -d); mkdir -p "$TMP/books"
cp -r prompts lint "$TMP"/
cp -r "books/<真实书名>" "$TMP/books/"
AINOVEL_HOME="$TMP" python -c "..."   # 一次性脚本：rebuild → 全章机检 → 打印结论
```

判据三条：不抛异常；机检不新增误杀（与改动前同章结论一致）；章节数与定稿状态不变。

**7. 1 章真模型对比（硬性项，不可跳过）**

适用：凡是动了**提示词、装配槽位、机检规则、审校 / 润色 / 定稿逻辑**的改动。

理由：单测只能证明流程没坏，证明不了稿子更好看。这是唯一能测质量的手段。

要求：

- 跑一章全链路，记录字数、各环节耗时、五维分数、与改动前同章的差异点。
- 结论三选一：**更好 / 无变化 / 更差**。判"更差"必须撤回或重做，不许"先上着看"。
- 这一步花真实 token 且约 4–5 分钟/章，**跑之前单独确认**（写进规格 §7 授权边界）。

## 6. 卡点清单（碰到就停，不许自己决定）

| 类别 | 具体事项 |
|---|---|
| 状态机 | 章节状态迁移、人工关位置（细纲确认、定稿二次确认） |
| 红线 | M-04 敏感词转人工且禁止自动改写；V5 未涉及句段改动率 >10% 丢弃；裁决队列非空禁止开下一章细纲 |
| 数据 | `books/` 文件格式、SQLite 表结构（必须保证"删库 → rebuild 完整恢复"）、归档与迁移 |
| 提示词 | 契约变更、变量增删（必须递增 frontmatter `version`） |
| 真实资源 | 碰真实 `books/` 或 `data/`、跑真实模型、打包发布 |
| 依赖 | 新增 Python 依赖（先确认没有标准库替代） |

## 7. 收口清单（每次改动结束都过一遍）

- [ ] 规格已写（L2 新建 / L1 增补）；与旧规格冲突处已回写并加交叉引用
- [ ] README「与规格的对应与偏差」已更新（若动了偏差行为）
- [ ] `docs/功能蓝图与差距.md` 对应项状态列已改（❌/🟡 → ✅）
- [ ] `docs/使用手册.md` 已更新（若用户可见行为变了）
- [ ] 验收报告已写（L2 必做；L1 只在批次文档记一行）
- [ ] 新发现的问题进 backlog，**不当场顺手做**
- [ ] `.workbuddy/memory/YYYY-MM-DD.md` 记一条（只记有长期价值的，不记临时路径和报错）
- [ ] 若交付 exe：`prompts/ lint/ web/dist` 已拷进 `dist/ai-novel/`（否则 exe 是旧的，你拿旧产物验新功能）
- [ ] commit 信息说清"改了什么 + 为什么"，一个功能一个 commit

---

## 8. 三种会让流程直接失效的情况

1. **一次改动塞进多个目标。** 复测失败时无法判断是哪个改动导致的。一次只做一件事，其余进 backlog。
2. **验收标准写成形容词。** "体验更好""更自然""更通顺"无法判定，等于没写。必须能被机械检查，或对应一个明确的手验动作。
3. **跳过基线直接跑全量。** 全绿也不知道是不是本来就有失败被掩盖。永远先记基线。

---

## 9. grill-me 使用规范

- 市场里显示名 `grill-me`（内部名 `grill-me-pro`）；同类还有 `grill-design`（需求拷问）、`grill-me-coach`（决策拷问）。任选其一，别同时装两个互相打架的。
- **只用于 L2 的需求层和方案层**。修 bug 时用它等于拷问"要不要修"，纯浪费时间。
- 开工前必须先喂 §4.1 的上下文。
- 它的天性是**扩大范围、追求全面**。所以每轮结束都要收一句"这条不做，原因是…"，最终落成规格 §0.2 的不做清单，否则会一路膨胀到做不完。
- 收敛后立刻落盘成规格，不要把结论留在对话里——对话会被压缩，结论会蒸发。
