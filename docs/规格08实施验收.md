### 3.3 A-T03 3000 字 Mock SSE（通过）

做法：本地 SSE mock 服务（每 20ms 推 2 字，共 3000 字，末尾发 `event: done`），用 CDP `Fetch` 域把
`/api/books/*/chapters/*/generate` 的请求改写到 mock 地址——**不改产物代码、不调模型**。
`scripts/spec08_browser_stream_conflicts.mjs`。

| 采样点 | 文本长度 | scrollTop | scrollHeight / clientHeight | 距底 ≤48px | 「回到最新」 |
|---|---|---|---|---|---|
| 上滚前（跟随中） | 704 | 665 | 1201 / 536 | 是 | 无 |
| 上滚到顶后 2.5s | 864（仍在增长） | **0（未被拉回）** | 1475 / 536 | 否 | 出现 |
| 点「回到最新」后 | 982 | 1151（=1687-536） | 1687 / 536 | 是 | 消失 |
| 冻结→恢复后 | 982 → 984 → … → **3000** | 1151 | — | 是 | 无 |

- 推流结束：最终长度 **3000**，尾字 `林寒压住令牌，指腹下的纹` 与期望完全一致。
- 渲染提交次数：整个 3000 字（1500 帧）期间 DOM 变更记录 **123 次**，远小于帧数 → 未逐帧重建正文段落列表。
- 后台恢复：`Page.setWebLifecycleState('frozen')` 2.5s 后恢复，推流继续到 3000 字完整。**如实标注**：这是"冻结态暂停后不丢尾字"，
  未覆盖"后台节流（throttled 而非 frozen）下流读取被降频但缓冲合并"的那条路径。

证据：`.pi/baseline/spec08-a03-a07-evidence.json`、`.pi/baseline/spec08-a03-stream.png`。

## 14. 「B 版更好，但仍有 AI 味」——诊断、W1 v7 上限约束与实测（2026-10-29）

### 14.1 用户判读（原文记录，不代签）

> 「B 版本读起来比 A 版本好多了，但是还是有股子 ai 味。」（2026-10-29 14:59）

据此：§11 第 3 项记 B 明显更优、倾向采用；「AI 味」作为独立质量问题在本节处理。

### 14.2 可测诊断（同一章、同一起点，逐项量化）

| 指标 | A legacy | B rolling | 人类网文常见区间 |
|---|---|---|---|
| ≤8 字成段占比 | 28% | **29%** | 10–20% |
| 最短段样例 | “五。”“四。”“逃不掉。” | “死路。”“不能停。”“不逃了。” | — |
| 段落均长 | 22 字 | 24 字 | 40–80 字 |
| ≥80 字段落 | 0 段 | **0 段** | 每章 ≥3 段 |
| 比喻词（像/如同/仿佛/般） | 5（1.9/千字） | **13（5.1/千字）** | ≤2/千字 |
| 数字报点（X 秒） | 2 | 3（28→20→11） | 1–2 |
| deslop 分数 | 41 | 56 | — |

**判断**：B 的画面感强于 A（这也是它读起来更好的原因），但代价是**比喻密度 2.6 倍**；两章共有病灶是
**通篇单句断行**（29% 段落 ≤8 字、没有一段超过 80 字），靠版面制造紧张，属于典型的模型默认戏剧化节奏。
W1 v6 的【表达】只写了「不强制固定停顿」，**没有任何上限**，所以模型一路顶着上限写。

### 14.3 W1 v6 → v7：四条「上限」而非模板

`prompts/write/W1.md` 新增【上限（不是模板，是天花板）】：段落节拍（连续 ≤10 字短段不超过 3 段）、
比喻配额（每千字 ≤2 处、相邻段不重复比喻词、喻体优先取本书设定内事物）、修饰克制（一名词一修饰语）、
报点克制（全章数字节拍 ≤2 次）。刻意写成**禁止项**而非「必须如何」，避免退回规格06 反对的套式化。

### 14.4 实测（同一副本、同一章、同一模型，只改 W1 版本）

| 指标 | B（W1 v6） | C（W1 v7） | 变化 |
|---|---|---|---|
| 字数 | 2571 | 2559 | 持平 |
| ≤8 字段落占比 | 29% | 25% | ↓4pp |
| ≥60 字段落 | 3 | **6** | ↑1 倍 |
| 比喻密度 | 5.1/千字 | **3.5/千字** | ↓31% |
| 数字报点（X 秒） | 3 | **1** | ↓ |
| 破折号 | 4 | 7 | ↑（未达预期） |
| 机检 warn | 11 | 16 | ↑（未达预期） |
| 五维 | 95/93/94/92/95 = 470 | 93/**96**/95/94/**98** = **476** | 本轮最高 |
| 生成耗时 | 70.2s | 61.4s | 更快 |

**结论：方向有效、幅度不够。** 4 项指标里有 3 项明显改善，但 25% 短段、3.5/千字比喻仍高于人类区间；
破折号与机检 warn 反而变多，说明单条上限会互相挤压（压了比喻就多用破折号断句）。

### 14.5 顺带验到的一件事：V2 润色兜不住结构型 AI 味

在 C 章上真实跑了一次 `pipeline.polish` → `reason_code="NO_CHANGE"`、`edits=[]`、候选与原文**字节相同**
（`chapters/revisions/9e8e33c5…/`）。原因符合 V2 的纪律：它只改「问题句段」、按词级/局部改写，
而本次 AI 味是**段落节拍与比喻密度**这类结构特征，没有可点名的错句 → 判定无需修改。
所以指望润色兜底是错的，杠杆只能在生成端（W1/W2/W5）与文风范例。

### 14.6 后续建议（按性价比排序，均需另行验证）

1. **本书文风范例**：`style/` 里放 2–3 段作者认可的人类范文，装配时进上下文——比继续加规则更能改「手感」；
2. **结构性检测**：给 deslop 增加「段落均长 / 比喻密度」两条**计量型**规则（当前 21 条全是词句级），让问题可见、可回归；
3. **不建议**继续给 W1 堆句子级规则：本轮已证明会挤压出别的毛病（破折号 +3、warn +5）。
