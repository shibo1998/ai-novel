## 0. 本规格的地位与核心决策

本规格是规格01—05的补充，不重新定义整套产品。批准后，只有下表列出的契约由本规格覆盖；其余既有约束继续生效。实施时必须在对应旧规格与 README 中添加明确交叉引用，不能只靠阅读顺序猜测优先级。

| 事项 | 当前行为 | 本规格批准后的行为 |
|---|---|---|
| 提示装配 | 模板元数据进入模型输入，系统段嵌在 user，W1上下文重复 | 元数据与指令分离，明确 system/user，各内容有唯一归属 |
| 文风应用 | 部分阶段只收特征卡或完全不收范文 | 生成、专项、长度调整、审校、润色使用一致的有效文风上下文 |
| M-12文风启发式 | 分数与结构性命中组合可能阻断 | 只作建议，不单独阻断或触发自动改写 |
| V2润色 | 整章改稿，检查通过后直接写正文 | 生成可追溯候选，经检查、差异预览、人工采纳后写正文 |
| V3复核 | 只收新稿和模型自报清单 | 同时收到原稿、候选及必要事实约束，分别判断保真与读感 |
| 文风分析F1 | 生成结果直接写特征卡 | 返回待编辑草案，人工保存后才成为正式特征卡 |
| 真实模型试验 | 不在本轮授权内 | 仍不在规格批准所授权的离线实施范围内 |

**必须保留的红线**：文件为真相源；原子写和格式校验；细纲人工确认；定稿二次确认；M-04敏感词转人工、禁止自动改写；V5未涉及句段改动率大于10%丢弃；裁决队列未清禁止开下一章细纲；正文改动使旧检查失效；同书互斥、修订号和指纹校验；调用日志和费用记录。

## 1. 目标、非目标与完成定义

### 1.1 本次目标

1. 减少由提示词固定配额造成的碎句、身体反应、解释总结、强制高潮等重复节拍。
2. 保留本书具体处境、人物关注点、技术动作、受伤代价与叙述态度，避免把“去味”变成统一口语、粗口或微动作模板。
3. 让同一本书在W1—W6、V1—V3、V5之间保持一致的文风规则和开关语义。
4. 每一份润色候选都能回答：基于哪版原稿、改了哪里、依据是什么、保真是否通过、是否已经人工采纳。
5. 将工程安全通过与作品更自然分别验收，不再以检测分数上涨代表文风改善。

### 1.2 明确非目标

- 不承诺AI检测器分数或“真人概率”。
- 不新增模型供应商、运行时Python依赖、向量数据库、微调或多代理写作架构。
- 不将V2变成生成主链的自动必经步骤，不增加无人确认的整本改写。
- 不改变已确认细纲中的事件、人物决定、信息揭露、伏笔与章末结果。
- 不给所有题材规定同一字长、段长、对白比例、情绪表达或标点习惯。
- 不自动修改真实书的文风卡、语料、提示词覆盖、历史正文或历史审校记录。
- 不改变当前模型路由与温度；参数对照留到提示目标稳定后另行验证。

### 1.3 完成定义

工程实现通过本文全部离线验收，称为“文风与安全编辑能力完成”。只有另行完成真实生成对照、人工盲评且达到§12门槛，才可称为“本批样本的文风改善已验证”。两种结论必须分别记录。

## 2. 总体流程

### 2.1 新正文主链

维持现有顺序：

`细纲生成 → 人工确认 → 统一文风与提示装配 → 正文生成 → 完整机检 → V1审校/V5修复 → 人工定稿 → 快照与记忆回写`

本规格不增加自动V2。M-12建议可以展示给作者和审校器，但不能仅凭句式、标点或规则分数触发自动V5。

### 2.2 手动安全润色

`用户请求 → 固定原稿与修订信息 → V2提出定点编辑 → 程序构造完整候选 → 保真与完整机检 → V3新旧稿对照 → 候选预览 → 人工采纳或放弃`

预览阶段不得写正式正文、更新正文修订号、推进主状态、作废原稿检查、写FTS或回写记忆。费用、调用日志和候选档案可以正常记录。

### 2.3 风格资料

`保存语料 → F1生成草案 → 人工编辑保存特征卡 → 可选确认范例片段 → 启用文风`

不因生成草案、更新语料或运行生成任务而静默覆盖现有特征卡。

## 3. 约束分层与文风裁决

### 3.1 三类规则

| 类别 | 例子 | 执行方式 |
|---|---|---|
| 内容及流程硬约束 | 已确认事件、人物已知信息、敏感词、字数范围、并发修订、文件格式 | 程序门禁与必要语义复核；不允许文风偏好豁免 |
| 作者表达要求 | 视角距离、叙述口气、对白风格、功能性停顿 | 以本书明确要求为准，生成和审校一致使用 |
| 通用文风建议 | 少重复解释、少空转情绪、注意节奏差异 | 按上下文举证，不按配额或单一词频判错 |

M-01、M-02、M-03、M-04及其他既有硬约束维持原契约。本规格只改变M-12/D系列作为文风启发式时的管线作用，不将敏感词或禁词硬规则混入建议层。

### 3.2 表达要求优先级

当前任务明确的表达要求 > 本书人工保存的特征卡及已确认范例 > 当前题材适配 > 全局通用建议。

这个优先级只能裁决表达，不能改动事实与流程。未经作者确认的F1草案没有正式特征卡的效力。

正文、语料、检索片段和改动理由都是素材，不作为程序指令执行；模型输出不得决定文件路径、调用工具或绕过门禁。

### 3.3 提示词修订要求

- 去掉“每章五件套各一次”“每200/300字固定节拍”“每场必须名场面”“每若干段插主观感受”等文体打卡要求。
- 已由细纲确定的关键决策、新信息和钩子继续保留；取消的是额外的统一文体配额。
- 允许有上下文依据的情绪和心理直写，不强制每次改成瞳孔、喉结、指节、呼吸等身体反应。
- 伤势、装备、场景约束要影响动作与选择；同一状态没有新增后果时不反复描写。
- 不用“随机走神、约数、粗口、故意说错”制造人味，不将理性决定改成冲动决定。
- 统一字数口径，删除S0/W1中独立于本次有效范围的固定2200—2800、2400收尾等硬编码要求。
- V1允许零条issues；有问题必须举证，不凑数量。
- 题材适配按有效genre_template选择；非都市题材不注入都市专属规则。缺省配置沿用现有默认值并在预览标注来源。
- 不增删或重命名现有提示词ID与文件；修改内容时递增frontmatter version。

## 4. 文风资产与一致消费

> 规格09 A补充六组手选候选与完整范围装配回归，复用本节文件/开关/预算；不自动导入候选、不自动采纳卡或启用真实书。

### 4.1 保留现有文件

- `style/语料.txt`：原始参考语料。
- `style/特征卡.md`：人工保存的正式特征卡，继续接受旧格式，不强制迁移或改写。
- `config.json.style_enabled`：唯一启用开关，缺失视为false。

有效开关关闭时，生成、长度调整、润色、V1与V3都不得注入书级特征卡、范例或书级风格评分要求。存在卡片不等于已启用。

### 4.2 特征卡草案

F1输出继续使用可读Markdown，并保留现有主要标题以兼容旧文件；每条特征应说明“观察、适用条件、例外或不确定性”。

- 不强制每维三条，不把单段样本的特征夸大成全书规则。
- 证据必须来自输入语料；样本不足允许明确写无法确定。
- 分析接口只返回草案，不写正式卡、不切换启用状态。
- 手工保存卡片时校验其基于的旧卡指纹；过期返回409，不覆盖用户其他页面已保存的卡片。

### 4.3 新增可选范例索引

批准实施后允许新增书级 `style/范例.json`，schema_version为1。它保存人工选择的语料范围，不另复制出第二套参考语料。

```json
{
  "schema_version": 1,
  "corpus_fingerprint": "64位SHA256",
  "examples": [
    {
      "id": "服务端生成的稳定ID",
      "start_paragraph": 1,
      "end_paragraph": 3,
      "scene_types": ["dialogue"],
      "content_fingerprint": "64位SHA256"
    }
  ]
}
```

- 段落号从1开始，由服务端对原始语料按空行解析；服务端保留原文范围，不要求浏览器计算Unicode偏移。
- 类型枚举：opening、dialogue、action、reasoning、transition、breakthrough、climax、general；这是检索标签，不是写作配额。
- 选择范围必须存在、完整、非空；保存时校验语料指纹。
- 语料变化后，旧索引标记stale，不套用到新位置，不自动改写索引。
- 老书没有范例文件时，允许从已有语料确定性选取完整段落作为兼容样例，明确标记legacy，不自动创建文件或宣称经过新增人工确认。
- 无可用范例时可只用已启用的特征卡，但预览必须说明缺失原因。

### 4.4 确定性选例

1. 先选与任务/场景类型匹配的片段，再选general。
2. 同等匹配按稳定ID排序；不使用random，不按生成时间随机换片。
3. 每次最多选择2段，总计最多1200个可见字符。这是输入预算上限，不是正文风格要求。
4. 超限只能舍弃完整范例，不从句中切断；没有能容纳的完整片段就不注入，并记录原因。
5. 相同语料、索引、任务类型与配置，必须选出相同范例并生成相同指纹。
6. W1—W5均可获得适用范例，W6、V1—V3、V5使用同一有效特征和相关范例引用。不能再出现前三章有卡无范例、审校关闭开关仍读卡的情况。

## 5. 提示装配、预算与调用证据

### 5.1 统一请求产物

在现有prompts/assembler基础上形成一个内部请求产物，至少包含：

- 实际发送的system与user文本；
- 主任务模板和参与子模板的ID、version、source、完整文件digest；
- 有效题材、文风开关、特征卡指纹、所选范例ID与指纹；
- 原稿/合同/上下文指纹；
- model、temperature、组装版本；
- system、user及各组成块的token估算；
- 兼容警告与发生的完整块截断记录。

`prompt_digest`仍保持当前“主模板完整文件摘要”的语义，不覆盖历史数据；组合请求另记request_digest。摘要相同不承诺远端模型逐字复现。

### 5.2 system/user分工

- frontmatter只用于加载、验证、温度和版本等运行参数，不发送给模型；`full_text()`仍可用于编辑、展示与文件digest。
- system放可信的角色定位、任务适用的全局规则、约束优先级；不能强制所有任务输出正文，V1/V2/V3等仍按各自结构输出。
- user放当前任务、唯一一份本章上下文/章合同、正文素材、范例和输出要求。
- W1中的上下文不再重复展开；合同作为上下文中的单一块，不在外层再复制。
- 请求标识符和素材边界必须清楚；不把范例内容当本书事实，不复制范例的角色名、情节或专有设定。

### 5.3 预算

继续复用现有token估算方式，但预算必须覆盖真正发送的system+user，包括外层模板、文风、范例和重试反馈。

超预算优先按现有顺序缩减FTS检索、摘要、Bible可裁剪条目，再舍弃完整可选范例。角色约束、已确认章合同、当前待编辑原稿、必要对照稿和硬规则不得静默截断。仍超限则返回可诊断的PROMPT_BUDGET_EXCEEDED，不发送残缺请求。

输入估算是工程近似，不宣称等于供应商精确token或上下文容量。输出截断、空结果和非法结构不得进入可采纳候选。

### 5.4 日志与预览

- 每次_call及格式纠错重试继续记录generation_log、tokens和费用；拒收候选不删除已发生的调用记录。
- generation_log轻量新增可空request_id与request_meta_json列；历史行允许为空，不反向伪造历史请求。
- 实际请求快照放在受忽略的data/assembly_previews下，以服务端生成的request_id索引，不接收任意文件路径。
- 不记录Authorization、API key或完整连接设置。预览中不需要暴露认证信息。
- 现有装配预览扩展为能查看实际system/user、总估算、参与模板与所选范例，避免“预览与实际请求不同”。

## 6. 上游细纲的重复节奏提醒

仅影响未来新生成或用户主动重新生成的细纲：

- G6额外参考最近3章已存在的核心事件、场景目标、钩子内容与类型，以及节奏任务；不得读取未来章作为已知事实。
- 提示要求比较是否重复使用同一种破局、倒计时、封路或威胁收尾，并解释本章与前文的区别。
- 可以在细纲Markdown中增加“节奏说明”，不新增必填frontmatter字段，不强制每隔几章插日常戏或兑现固定数量伏笔。
- 相似度和语义重复只作人工提醒，不据此自动改动已确认细纲。
- 既有钩子类型校验、FO合法性和人工确认保持不变。
- 正文编辑器发现问题来自剧情结构时，只报告，不在润色阶段偷改事件。

## 7. V2定点编辑与V3双重判断

### 7.1 V2接口版本

V2、V3新增frontmatter `interface_version: 2`，保留现有必填字段并递增version。版本2的V2不再输出任意整章改稿字符串，而是结构化编辑建议。

服务端把原稿解析为带稳定block_id的块，保留准确原文和分隔符。浏览器只传block_id，不传自行计算的字符位置。

```json
{
  "edits": [
    {
      "start_block": "p0012",
      "end_block": "p0014",
      "original": "服务端原稿中该范围的完整原文",
      "replacement": "替换后的文本",
      "category": "重复解释",
      "reason": "有原文依据的修改原因"
    }
  ]
}
```

- 默认模式为自动寻找有证据的问题；可选selected模式只处理用户选中的原文块。
- 允许edits为空；没有必要修改时直接返回no_change，不为完成任务凑改动。
- 范围必须存在、不重叠，original与原稿范围逐字一致；replacement不得为空，不允许通过空替换整段删除剧情信息。
- 服务端按原稿范围应用编辑，构造完整候选；未涉及区域及分隔符逐字保留。
- 多个原段可以合并为一个新段，也可在范围内拆分，解除“段落数不变”；仍受字数与骨架保护。
- 非法JSON、越界、原文不匹配、越过用户选区、整章自由重写冒充补丁，全部拒收，不落正式稿。
- 不再硬编码“都市修真底层写实”；使用当前书有效文风、人物声音与事实约束。

### 7.2 程序保真检查

对服务端构造的完整候选，保留并全部执行：

1. 与原稿字数浮动不超过±10%。
2. 去空白长度比0.55—1.9。
3. 句末标点数量不少于原稿60%。
4. 原稿不同4字串至少30%仍存在。
5. 完整机检必须pass，不是只检查hits。
6. 规则未生效仍按既有not_effective处理，不伪造通过。
7. 原稿命中M-04时，不调用V2；候选新命中红线时拒收，不调用自动修复器改敏感词。
8. 显式length截断、空结果、结构解析失败拒收。

这些检查是保守护栏，不等于语义证明。需要超过现有边界的大改，提示用户分段处理或通过人工正文编辑完成，本规格不新增“强制放行”开关。

### 7.3 V3输入与输出

输入至少包含：原稿全文、候选全文、服务端真实编辑清单、当前有效章合同、必要角色声音/底线、知情边界及有效文风。无细纲导入章明确标记合同缺失，不伪造合同，按原稿与现有档案核对。

保真检查维度：事件与因果、人物决定与人设、信息揭露、设定/数字/能力代价、时空与关系、伏笔及章末结果。每个维度输出pass/fail/unknown；确实不适用时给出理由。

读感另输出style_verdict：improved、unchanged、worse、unknown，并引用真实修改前后文本说明。问题清单允许为空，不能把增加粗口、微动作或戏剧性当作固定加分项。

保留clean、verdict、new_issues等可识别字段，但clean只表示本次复核的通过结论，不代表AI检测概率。

可进入ready的必要条件：程序全部通过、保真明确通过、style_verdict为improved、clean=true、verdict=pass、没有未解决的阻断问题。unknown或worse保留原稿；unchanged返回no_change或不可采纳候选，不强行写回。

V3仍可能判断错误，因此人工采纳不可省略。普通润色最多一轮V2加一轮V3；格式纠错沿用已有有界重试，不另起无限“改到高分”循环。

## 8. 候选存储与生命周期

### 8.1 存储位置

新增书级档案目录，不新增候选数据库表：

```text
chapters/revisions/<candidate_id>/
  source.md
  candidate.md
  manifest.json
```

- candidate_id为服务端生成的固定格式UUID，接口只能接收合法ID，禁止路径片段。
- source.md保存生成候选时的正式正文快照；candidate.md保存候选完整正文，均使用UTF-8、显式newline、frontmatter校验和atomic.write_text。
- manifest.json有严格schema校验，最后原子发布，作为候选可见的提交标志；不完整目录不得当作ready。
- 存储原稿/候选指纹、书与章、源版本、源修订号、源状态、依赖事实/合同/文风/规则指纹、请求ID、模板证据、编辑清单、检查结果、生命周期与采纳回执。
- FTS、正文装配、导出txt/md、记忆卡和定稿只消费正式正文，不能误扫此目录。
- rebuild直接从文件恢复候选可见性，不给候选伪造章节主状态；删除SQLite不会丢失待采纳文本。
- v1不自动清理候选，不给旧书批量创建目录。

### 8.2 状态

生命周期：generating → ready / rejected / no_change / error / interrupted；ready → applied / discarded / stale。采纳提交期间使用applying恢复标记，它不是章节主状态。

ready必须同时满足全部检查。只要正文修订、正文文件、状态、合同、相关事实或有效文风/规则依赖变化，原候选变为stale，不自动套到新稿。候选不按时间任意过期，也不在过期后自动重新生成。

rejected候选可以展示原因与差异，但采纳按钮必须禁用。用户可回到正常正文编辑流程处理，不能绕过候选门禁强行采纳。

### 8.3 重复请求与异常

- 创建候选要求client_request_id；相同ID和相同请求返回既有结果，不重复调用模型。
- 相同ID却换书、章、修订号或选区，返回409 IDEMPOTENCY_CONFLICT。
- 已在生成时返回409 TASK_RUNNING或既有任务描述，不再发起第二份任务。
- 模型调用中进程退出，无法确认远端是否已完成时标记interrupted。同ID重试不自动再次计费；新请求必须使用新ID并提示可能重复发生费用。
- 网络或解析失败不改变正式正文；费用与失败日志保留。

## 9. 人工采纳、并发与中断恢复

### 9.1 采纳前置条件

在同书写锁内重新读取并验证：

- 候选属于当前书与章，candidate_fingerprint与文件内容一致，状态ready。
- 当前正式稿的完整文件指纹、正文指纹、current_version、state_revision、主状态与候选基线一致。
- 当前主状态仍为pending_finalize或human_review；finalized必须先走既有解锁流程。
- 所依赖的合同、角色/知情边界、文风和规则指纹仍有效。
- 重跑确定性检查，且此前V3结果有效；不在采纳时偷偷追加一次模型调用。

任意不一致返回409并保留两份文本，不允许force=true覆盖。

### 9.2 写回语义

- 采纳必须复用chapters.write_prose及其修订和检查失效机制，不能绕过统一写入口。
- 成功后保持当前稿件分支版本号，正常递增修订号；正文与候选一致，主状态回mech_check，旧机检、审校与豁免对新正文失效。
- 此操作不是定稿，不生成final标记，不调用V4/V6，不更新角色或记忆。
- 记录一次kind=polish的应用记录及candidate_id；再次采纳同一已applied候选返回原回执，不二次改正文或重复递增修订。
- 用户在候选生成后手改正文、切章、重新定稿或改合同，均不得被旧候选覆盖。

### 9.3 故障恢复

采纳前在manifest中原子写入applying信息和有界恢复数据：原稿快照、目标指纹、相关本章索引前态及应用标识。整个流程持有同书锁。

- 普通异常：恢复本次涉及的正文与本章索引，保持模型调用/费用历史，不回滚无关书档案。
- 进程中断后：如果正文仍是source，恢复或保持可重试前态；如果正文已是candidate，幂等完成检查失效、状态与回执；不得再次调用模型。
- 如果发现第三种正文、无法匹配的修订或外部改动，标记recovery_required，不自动覆盖。该章正文写入与定稿先提示恢复，读取与文本导出仍可用。
- 必须覆盖“正文已替换但索引未更新”“索引已更新但回执未发布”等故障注入点。

不能宣称文件与SQLite天然具有跨介质事务；实现必须通过恢复标记和幂等规则保证可解释的结果。

## 10. API契约

### 10.1 文风接口

- `GET /api/books/{book}/style`：保留corpus/card/enabled，新增两者fingerprint、范例索引、stale与兼容警告。
- `POST .../style/analyze`：返回草案card、来源指纹、模板digest、applied=false；不写正式卡、不自动启用。
- `PUT .../style/card`：保存人工文本；前端必须携带expected_fingerprint，过期409。旧客户端未传时继续兼容，但响应明确没有并发保护，仓库前端必须升级。
- `PUT .../style/corpus`：保留现有文本输入；仓库前端增加expected_fingerprint。旧范例过期按读取时指纹计算，不偷偷套新位置。
- 新增 `PUT .../style/examples`：提交语料指纹及段落范围/标签，服务端校验并原子保存。
- 文风切换接口路径不变，开关必须作用于整条链。

### 10.2 创建候选

沿用 `POST /api/books/{book}/chapters/{no}/polish`，**明确改变为预览语义，不再直接写稿**。仓库前后端必须同时升级。

```json
{
  "expected_revision": 18,
  "client_request_id": "UUID",
  "mode": "auto",
  "selected_blocks": []
}
```

selected模式必须带有效block_id；auto模式由V2定点找问题。服务端返回候选ID、status、ready、applied=false、原稿/候选指纹、before/after字数、真实编辑、程序检查、V3结果及费用摘要。

旧无请求体调用可以返回可理解的预览结果与升级警告，但绝不能保留自动写回后门。ok只表示请求处理成功，不能表示正文已变。

### 10.3 候选读取与操作

- `GET .../polish/candidates`：当前章候选列表。
- `GET .../polish/candidates/{id}`：原稿、候选、diff数据、检查与当前是否stale。
- `POST .../polish/candidates/{id}/approve`：必传expected_revision、source_fingerprint、candidate_fingerprint；返回applied、采纳后的修订号/状态和回执。
- `POST .../polish/candidates/{id}/discard`：幂等放弃，不改正文；已applied不能借此回滚正文。

状态码：字段/选区非法422；不存在404；并发、过期、升级要求、恢复中409；外部模型故障502或沿用现有错误映射。正常拒收候选可返回200加ready=false与稳定reason_code，不能伪报applied。

## 11. UI要求

保持Vue3、Element Plus和现有信息密度，不重做页面风格。

### 11.1 工作台

- “整章润色”改为“生成润色候选”，说明不会直接覆盖。
- 可对原稿选定连续段落后生成定点候选；默认仍可自动找问题。

M-12/D系列文案统一为“文风规则提示，非AI生成概率”。规则分数保留兼容展示，不作为“可以发布”的主结论。

装配面板能看到实际system/user、有效文风、范例、模板来源与预算；旧书覆盖导致的兼容模式必须可见。

- 没有作者盲评和真实结果时，只能报告工程验收完成，不能报告去味已成功。

- 不批量重写旧书文件、书级配置、历史检查或已有覆盖提示词。

- 旧覆盖中仍有重复上下文或固定配额时，预览提示其尚未升级，不擅自改写用户模板；新一致性保证针对升级后的全局/书级模板。
- V2/V3必须支持interface_version=2才能进入新候选流程；旧书级覆盖不兼容时，在调用前返回PROMPT_UPGRADE_REQUIRED，列出待升级ID。禁止静默忽略书级覆盖或把旧自由整章输出当安全补丁。
- M-12改为建议是本规格的显式行为变更。旧deslop配置可以继续读取，原blocking标签作为历史/配置来源展示，但新管线不据此单独阻断或自动改写；前端必须解释有效处理级别，不能悄悄保留旧拦截。
- generation_log新增列可空迁移；旧程序不使用这些列。候选目录不参与章节枚举；回退代码不自动删除它。
- 回退发布时保留所有候选、来源快照与日志；已人工采纳的正文不能因为回退版本而自动还原。恢复旧稿仍须走人工确认和修订校验。
