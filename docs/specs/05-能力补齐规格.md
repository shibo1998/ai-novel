## 1. 贯穿原则：失败关闭（fail-closed）

四条，所有新检查器与旧检查器改造都必须满足。违反其一即为实现缺陷。

### P-1 结论三态，禁止二态

任何检查器返回的结论必须是三者之一：

| 结论 | 含义 | 下游动作 |
|---|---|---|
| `pass` | 规则**全部生效**且无阻断 | 允许推进 |
| `blocked` | 规则**全部生效**，有阻断 | 拦截 |
| `not_effective` | 至少一条阻断级规则**未生效** | **禁止推进**，转人工并显式提示"哪条没查" |

`not_effective` 不等于 `pass`，也不等于 `blocked`。它的语义是「这次没查成」，不是「查了没问题」。

### P-2 未生效必须可见，且必须能被断言

每个检查器返回体带 `ineffective: [{rule, reason, detail}]`。`reason` 枚举固定：

```
missing_file      规则文件不存在
empty_file        文件存在但 0 条有效规则
suspiciously_small  规则数低于健康下限（见 §2.3）
bad_threshold     阈值配置非法（区间倒置/负数/非数字）
disabled          显式关闭
unparsed          输入解析为空（正文 0 字、章节文件缺失）
crash             检查器异常
```

前端必须把 `ineffective` 显示成**警示条**（红色），文案：「本次未检查：M-02 禁词（词表文件缺失）」——不允许折叠进"通过"。

### P-3 结论绑定内容指纹

任何"通过"结论必须记录它判定的是哪一版正文。正文一变，结论即过期。过期结论不得作为推进依据。

```
fingerprint = sha256(normalize(body))[:16]
normalize: 去 frontmatter → 统一 \r\n 为 \n → 去行尾空白 → 折叠连续空行为单空行
```

**不得用 mtime 判定**（既会假过期也会假绿）。

### P-4 禁止静默降级

任何降级（FTS 不可用转 bigram、词表缺失跳过、LLM 返回解析失败重试）都必须在返回体留痕。删掉一条规则必须是一次显式提交，不能因为"读不到"而发生。

## 2. F-01 假绿防护

### 2.1 现状缺陷

| 位置 | 缺陷 | 后果 |
|---|---|---|
| `ainovel/mechcheck.py:31-40` `_load_lines()` | 文件不存在返回 `[]`，不报错 | M-02/M-03 空转 |
| `ainovel/mechcheck.py:64` `check()` | 返回 `list[Hit]`，无法表达"没查" | 调用方无从区分 |
| `ainovel/pipeline.py:615` `run_mech_check()` | 只看 `has_block(hits)`，无 block 即 `pass` | 词表清空 → 整章直接进 llm_review |
| `ainovel/api.py:796-807` | 返回 `{hits, status}` | 前端拿不到未生效信息 |
| `review_records` 表 | 只有 `issues_json` + `verdict`，无指纹 | 正文改动后旧结论仍显示为"已通过" |
| `settings.mechcheck` 阈值 | 非法值（如 `word_range=[3000,2000]`）不报错 | M-01 永不触发 |

### 2.2 目标

机检从「返回命中列表」升级为「返回一次带生效状态的检查结论」。

### 2.3 数据契约

`ainovel/mechcheck.py` 新增：

```python
@dataclass
class Ineffective:
    rule: str           # M-02
    reason: str         # 见 P-2 枚举
    detail: str         # "lint/banned_words.txt 不存在"

@dataclass
class CheckResult:
    hits: list[Hit]
    ineffective: list[Ineffective]
    verdict: str        # pass | blocked | not_effective
    fingerprint: str
    word_count: int
    checked_at: str

    def to_dict(self) -> dict[str, Any]: ...
```

`check()` 签名保持不变（返回 `list[Hit]` 以兼容 3 处旧调用），新增 `check_full()` 返回 `CheckResult`。**新代码一律调 `check_full()`**，`check()` 标注 deprecated。

### 2.4 生效判定表

| 规则 | 依赖 | 未生效条件 | 级别 |
|---|---|---|---|
| M-01 字数 | `chapter_word_range` | 区间非 2 元素 / 非递增 / 含负 | **block 级** |
| M-02 禁词 | `lint/banned_words.txt` | 缺失 / 0 条 / < 20 条（记 `suspiciously_small`，降为 warn） | 缺失与 0 条为 **block 级** |
| M-03 对话后缀 | `lint/dialog_suffix.txt` | 缺失 / 0 条 | warn 级 |
| M-04 敏感词 | `lint/sensitive_words.txt` | 缺失 / 0 条 | **block 级**（红线词表空 = 等于没红线） |
| M-05..M-11 | 内置常量 | 正文 < 100 字（`unparsed`） | warn 级 |

判定汇总规则：

```
ineffective 中存在任一 block 级规则 → verdict = not_effective
否则有 block hit                → verdict = blocked
否则                            → verdict = pass
```

### 2.5 流程变更（`pipeline.run_mech_check`）

```
res = mechcheck.check_full(...)
_record(res)                       # review_records 增 fingerprint/verdict/ineffective
if res.verdict == "not_effective":
    transition("blocked_after_fix")   # → human_review，必须人工处理
    return res
if res.verdict == "pass":
    transition("pass")                # → llm_review
    return res
... 原自动修复分支不变
```

`human_review` 落点后，前端提示：「机检未完整执行：M-02（词表缺失）。修复后点重跑机检」——文案必须点名规则，不能只说"检查异常"。

### 2.6 指纹与过期

DB 变更：

```sql
ALTER TABLE review_records ADD COLUMN fingerprint TEXT;
ALTER TABLE review_records ADD COLUMN ineffective_json TEXT;
ALTER TABLE chapters ADD COLUMN checked_fingerprint TEXT;
ALTER TABLE chapters ADD COLUMN checked_status TEXT;       -- pass|blocked|not_effective
```

写入点：

| 事件 | 动作 |
|---|---|
| 机检（`run_mech_check`） | `chapters.checked_fingerprint = res.fingerprint`，`checked_status = res.verdict` |
| 正文任何写操作（`PUT /prose`、`/prose/correct`、`/fix`、`/rewrite`、`/polish`） | 计算新指纹；与 `checked_fingerprint` 不等则 `checked_status = 'stale'` |

状态机配合：现有规则已在 `pending_finalize` 手改后强制 `recheck → mech_check`（`statemachine.py:48-50`），本项**不新增转移**，只补「结论失效」这一数据侧面，供 UI 与审计使用。

新增只读端点：

```
GET /api/books/{book}/chapters/{no}/checkstatus
→ { verdict, checked_at, checked_fingerprint, current_fingerprint,
    stale: bool, ineffective: [...], hits_count: {block: n, warn: n} }
```

### 2.7 验收

- **T-01** 删除 `lint/banned_words.txt` → `mechcheck` 返回 `verdict=not_effective`，`ineffective` 含 `M-02/missing_file`，章节状态落 `human_review`，**不得**进 `llm_review`。
- **T-02** `banned_words.txt` 只留 3 条 → `ineffective` 含 `M-02/suspiciously_small`，`verdict` 仍按 hits 判定（不当阻断），但 UI 显示警示条。
- **T-03** `config.chapter_word_range = [3000, 2000]` → `ineffective` 含 `M-01/bad_threshold`，`verdict=not_effective`。
- **T-04** 正常书 → `ineffective` 为空数组（不是缺失字段），`verdict` 与旧行为一致。
- **T-05** 机检通过后手改一字 → `GET checkstatus` 返回 `stale=true`，`checked_status` 字段为 `stale`。
- **T-06** 同一段正文两次机检 → `fingerprint` 相同（稳定性）。

## 3. F-02 AI 味确定性检测器

### 3.1 现状缺陷

「AI 味」只有一个来源：V1 审校 LLM 给的 `ai_flavor` 主观分（`pipeline.py:972` `RUBRIC_DIMS`）。缺陷：

1. **不可解释**：说 92 分，但哪句像 AI 说不出来，无法定点修。
2. **不可回归**：换模型后分数漂移，无法判断是文本变了还是模型变了。
3. **可被讨好**：LLM 常给高分，第 12 章 68→86 的抬升无法验证真伪。
4. **零 token 规则本该先跑**，现在完全依赖付费调用。

### 3.2 目标

新增 `ainovel/deslop.py`：纯规则、零 token、可解释、**只报不改**。输出命中清单 + 0–100 干净度分。

### 3.3 规则集（21 类）

权重约定：`L1=12`（强特征，出现即像 AI）/ `L4=8`（句式模板）/ `L2=5`（中特征）/ `L3=2`（弱特征，仅密度计）。

| ID | 名称 | 检测方式 | 阈值 / 参数 | 层级 | 级别 |
|---|---|---|---|---|---|
| D-01 | 否定对举 | `不是…?而是`、`并非…?而是` | 每次命中 | L4 | **blocking** |
| D-02 | 反向否定 | `不但/不仅/不光 … 反而/反倒` | 每次 | L4 | advisory |
| D-03 | 声音反差 | `声音不大却带着`、`语气平淡却` | 每次 | L4 | **blocking** |
| D-04 | 否定排比 | 连续 ≥3 句以 `没有/不再/不曾` 起 | 3 句 | L4 | **blocking** |
| D-05 | 破折号 | `——`、`--` | 出现即计 | L1 | **blocking** |
| D-06 | 升华式收尾 | 末 200 字含 `他知道`/`从这天起`/`一切才刚开始` | 末段 | L4 | **blocking** |
| D-07 | 总结式收尾 | 末段含 `总之/由此可见/这一刻，他明白` | 末段 | L2 | advisory |
| D-08 | 三段排比 | 同结构分句连续 3 组（长度差 <15%） | 3 组 | L4 | advisory |
| D-09 | 微动作套式 | `嘴角勾起/眼中闪过/眼底划过/心中一凛/眉头微皱` | ≥5 次且 ≥6/千字 | L1 | advisory |
| D-10 | 套式反应 | `深吸一口气/喉咙一紧/心里一沉/拳头攥紧` | ≥4 次/1.5千字 | L2 | advisory |
| D-11 | 动作清单 | 单段内 `先…然后…接着…最后` 或 4+ 个 `又…` 并列 | 每次 | L4 | advisory |
| D-12 | 抽象总结 | `这一切都/说明/意味着/预示着` | ≥3 次/4千字 | L2 | advisory |
| D-13 | 陈词密度 | `仿佛/似乎/宛如/犹如/恍若` | >2 次/章 | L3 | advisory |
| D-14 | 比喻密度 | `像/如同/好似` + 抽象宾语 | ≥7 次/3千字 | L3 | advisory |
| D-15 | 因果链套式 | 同段 `因为…所以…于是` 或 `由于…因此` | 每次 | L2 | advisory |
| D-16 | 系统提示腔 | `叮！/恭喜宿主/检测到/结算如下` 且非对话内 | 每次 | L1 | **blocking** |
| D-17 | 过度压缩电报体 | 连续 ≥6 句均 <8 字 | 6 句 | L3 | advisory |
| D-18 | 连接词稀薄 | `而/但/却/于是/因此` 密度 <1.5/百字 | 全文 | L3 | advisory |
| D-19 | 句号断续 | 连续 ≥5 句以句号结尾且无逗号 | 5 句 | L3 | **blocking** |
| D-20 | 超长段 | 单段 >120 字 | 每段 | L1 | advisory |
| D-21 | 引号强调腔 | `所谓"…"`、`这就是"…"` | 每次 | L2 | advisory |

**blocking 规则只报 L1/L4 里明确的结构性硬伤**，语义类一律 advisory——避免又出现"护栏误杀"（P1 曾因越权护栏两次拒绝合法修改）。

### 3.4 保护区（`preserve`）

命中以下区间内的字符**不检测、不计分**：

| 保护区 | 正则/规则 |
|---|---|
| 对话引号内 | `[「『“][^」』”]*[」』”]` |
| 数字 + 单位 | `\d+(?:\.\d+)?\s*(?:米|里|丈|尺|年|月|日|天|人|个|次|成|层|级|阶|品|枚|柄|把)` |
| 专名标记 | `【[^】]{1,20}】` |
| 书名号 | `《[^》]{1,40}》` |
| 已有完整比喻句 | `(?:像|如同|仿佛)[^。！？]{6,40}[。！？]`（整句冻结，防被撕碎） |

保护区实现：先算出 `[(start, end)]` 区间集合，命中点在区间内的直接丢弃。

### 3.5 打分

```
raw    = Σ(hit.weight)                      # L1=12 L2=5 L4=8；L3 只参与密度惩罚
density_penalty = Σ(超阈值规则的超限量 × 2)
base   = max(word_count, 300) / 1000
per_k  = (raw + density_penalty) / base

# 罚分：per_k 越大越脏，饱和映射到 0–100 的罚分
penalty = 100 * (1 - exp(-per_k / 36))

# 输出的是「干净度」，与 V1 审校 ai_flavor 同向：越高越干净
ai_flavor_score = round(100 - penalty)
```

**方向必须与 V1 的 `ai_flavor` 一致（高=干净）**。今天已踩过一次「术语预检方向反」的坑，实现时必须写一条断言：喂一段满是 D-01/D-05 的文本，`ai_flavor_score` 必须显著低于干净文本。

### 3.6 集成

**（a）接入机检为 M-12**

```
M-12 AI 味     warn when ai_flavor_score < 60
               block when ai_flavor_score < 45（可配 mechcheck.ai_flavor_block）
```

默认阈值刻意放宽，先只做"报警"不做"拦路"，观察真实书 20 章后再收紧。阈值走 `settings.mechcheck.ai_flavor_block`。

**（b）作为 V1 审校的客观证据**

审校变量新增 `检测器结果`（top 8 命中，格式 `D-05 第12行 "——"`）。提示词加一句：「以下为规则检测器的确定性命中，可作为 ai_flavor 打分依据；不要因为检测器未命中就给高分」。**这是防止 LLM 瞎打分的关键约束**。

**（c）作为 V2 润色的靶子**

`deslop_hits` 直接进 V2 提示词，替代现在笼统的「去 AI 味」要求。

### 3.7 验收

- **T-07** 用 `D:/1-work/oh-story-claudecode/demo/去AI味对照/改前.md` 与 `改后.md` 跑检测：改前分必须低于改后分，差值 ≥10。
- **T-08** 保护区不误报：构造 `他说："不是这样，而是那样。"` → D-01 不命中（在对话内）。
- **T-09** 方向断言：全 `——` 的文本 `ai_flavor_score < 45`，纯白描文本 `> 80`。
- **T-10** 幂等：同一文本两次检测结果完全一致（无随机、无时间依赖）。
- **T-11** 空正文 → 返回 `unparsed`，不返回 0 分（0 分会被误读成"极脏"或"极干净"）。
- **T-12** 性能：3000 字正文检测 <80ms（纯正则 + 单次遍历）。

## 5. F-04 记忆卡补做入口

### 5.1 现状缺陷

`pipeline.py:1405-1406`：

```python
# 记忆卡失败不回滚定稿，但标记待重试
statemachine.mark_error(book, no, f"记忆卡回写失败: {e}")
```

问题：定稿仍成立（合理，不该因回写失败丢稿），但**没有任何入口把这次回写补上**。后果是这一章的事实永久缺席长期记忆：角色状态、伏笔推进、新地点全丢，而章节显示 `finalized`，下游毫无提示。

### 5.2 目标

可列出缺卡章、可单章补做、可批量补做，且补做幂等。

### 5.3 接口

```
GET  /api/books/{book}/memory-card/pending
→ { chapters: [{no, title, reason, status, has_card, errored_at}] }

POST /api/books/{book}/chapters/{no}/memory-card/rebuild
→ { ok: true, chapter_no, applied: {char_updates: n, foreshadow_ops: n,
     new_chars: n, new_locations: n, state_entries: n} }
→ 409 当 status != finalized
→ 500 当 LLM 仍失败（保留原标记）

POST /api/books/{book}/memory-card/rebuild-batch
body: { chapters: [1,2,3] } 或 { all_missing: true }
→ { queued: n }   # 逐章串行，失败不阻断后续，最后返回汇总
```

`pending` 判定：`status == 'finalized'` 且 `chapters/<no>_记忆卡.md` 不存在，**或**记忆卡 frontmatter 的 `fingerprint` 与当前正文不一致（F-05 引入）。

### 5.4 幂等性

补做必须先清理该章已产生的派生结果，否则会重复推进伏笔：

1. 删 `chapters/<no>_记忆卡.md`
2. 回滚该章的 `foreshadow_ops`（依据记忆卡里记的 `applied_ops`；若卡不存在则依据 `PLOT_POINTS.md` 的 `last_op_chapter == no` 条目回退到 `planted/building`）
3. 回滚 `characters` 的角色状态（该章 `char_updates` 写入的字段）→ 从上一章记忆卡的快照恢复
4. 重跑 V4
5. 重新 apply

**这条必须在实现前想清楚**：`apply_status_updates` 与 `apply_foreshadow_ops` 现在是"只前进"的写入，没有回滚。F-05 的状态快照正是提供回滚基线的手段——所以 **F-04 的完整实现依赖 F-05**。若 F-05 未完成，F-04 v1 只支持「卡不存在」的补做（此时无重复风险），不支持「卡存在但过期」的重做。

### 5.5 验收

- **T-16** 构造：定稿后删掉记忆卡 → `pending` 列出该章 → `rebuild` 成功 → `pending` 清空。
- **T-17** 非定稿章调 `rebuild` → 409。
- **T-18** 连续两次 `rebuild` → 伏笔状态与角色状态**不重复推进**（`PLOT_POINTS.md` 的 `状态` 不变，`characters` 状态不变）。
- **T-19** LLM 失败 → 返回 500，`pending` 仍列出该章（不能因为失败就认为已处理）。

## 6. F-05 按章状态快照（StateDelta）

### 6.1 现状缺陷

长期记忆目前是**叙述性文本**：V4 记忆卡输出 `event_summary` + `char_updates`（自由文本字段），装配槽 `char_cards` 读角色卡。

由此产生三个不能：

1. **不能机检**：第 12 章说「林寒断了两根肋骨」，第 15 章说他背人跑三里地——只有 LLM 能发现，规则层完全看不见。
2. **不能回滚**：角色状态是覆盖写，改错了没有基线可回。
3. **不能量化弧光**：`arc_stage` 只存在于 `characters/*.md` 的「弧光预设」文本里，没有按章序列。

### 6.2 目标

把「每章发生了什么」变成**结构化事实**：每章一份状态增量，落地为表，派生为人读状态卡。

### 6.3 数据契约

**DB 表**（新增）：

```sql
CREATE TABLE IF NOT EXISTS chapter_state (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    book_id INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    chapter_no INTEGER NOT NULL,
    character TEXT NOT NULL,
    location TEXT,
    physical TEXT,                 -- 伤势/疲劳/衣着
    mental TEXT,                   -- 情绪/动机
    power_level TEXT,              -- 战力口径，必须命中 Bible 境界序列
    arc_stage TEXT,                -- 弧光阶段（0-5 或自定义枚举）
    knowledge_json TEXT,           -- 该角色本章结束"已知"的事实 key 列表
    goals_json TEXT,               -- 当前目标
    delta_json TEXT,               -- 原始增量，用于回滚
    fingerprint TEXT,              -- 对应正文指纹
    created_at TEXT NOT NULL,
    UNIQUE(book_id, chapter_no, character)
);
CREATE INDEX IF NOT EXISTS idx_chapter_state_lookup
    ON chapter_state(book_id, character, chapter_no);
```

**V4 JSON schema 扩展**（`chapters.MEMORY_SCHEMA`）：

```python
"required": [..., "state_delta"],     # 新增为必填（新书生效）
"types": {
    ...
    "state_delta": list,              # [{character, location, physical, mental,
                                      #   power_level, arc_stage, knowledge, goals}]
}
```

**兼容处理**：老记忆卡没有 `state_delta`。`MEMORY_SCHEMA` 加 required 会让 `read_memory()` 在验证老文件时失败（今天 Bible 表头校验误伤整本书的教训）。

因此拆分：

```python
MEMORY_SCHEMA_V1 = 现有 schema（无 state_delta）
MEMORY_SCHEMA    = 新 schema（含 state_delta，required）
read_memory(): 先按 V2 校验，失败则按 V1 校验并标 legacy=True（不报错）
```

**派生文件** `books/<书名>/STATE.md`（人读，每章覆盖式重建，≤12KB）：

```markdown
# 当前状态（截至第 15 章）

## 1. 当前位置与时间
## 2. 核心角色状态（只列 `role` 为主角/反派/重要配角的角色）
| 角色 | 位置 | 身体 | 心理 | 战力 | 弧光 |
## 3. 关系张力（近 3 章有变化的边）
## 4. 未回收伏笔（≤15 条）
## 5. 近三章速记（各 ≤60 字，来自 event_summary）
## 6. 下一章承诺（来自细纲 hook）
## 7. 连贯性风险（机检 + 审校累积未解项）
```

重建时机：每次 `writeback_memory` 成功后。**派生文件不得手改**（写操作一律走 V4），文件头写 `<!-- generated by V4; do not edit -->`。

### 6.4 装配变更

`char_cards` 槽的取数改为：

```
优先：STATE.md 第 2 节中本章出场角色的行（结构化、短）
回退：characters/*.md 角色卡全文（STATE.md 缺失时）
```

新增 `state_card` 槽？**不加槽**（不破坏 13 槽预算）。`recaps` 槽改为读 STATE.md 第 5 节（近三章速记）+ 原有前情摘要兜底。

### 6.5 可机检项（新增 M-13 ~ M-15）

| 规则 | 判据 | 级别 |
|---|---|---|
| M-13 战力倒退 | `power_level` 在 `realm_order()` 中索引**小于**上一章 → 阻断 | block |
| M-14 死者复现 | 角色卡 `状态=死亡` 且本章 `chapter_state` 有行动记录 | block |
| M-15 位置跳跃 | 本章 `location` 与上章不同，且正文无位移描写（关键词：走/赶/飞/船/车/月/日） | warn |

M-13 复用已有的 `realm_order()`（`bible.py`，已修 markdown 污染）。M-13/M-14 是**真阻断**，比现在只靠 LLM 审校可靠。

### 6.6 验收

- **T-20** 第 N 章 V4 返回含 `state_delta` → `chapter_state` 落 3 条记录，`STATE.md` 对应行更新。
- **T-21** 老记忆卡（无 `state_delta`）→ `read_memory` 不抛错，`legacy=True`，装配走回退路径。
- **T-22** 构造：第 5 章 `power_level=感气境`，第 6 章 `power_level=筑基境`（序列更早）→ M-13 报 block。
- **T-23** 构造：角色 `状态=死亡` 后第 3 章又有 `state_delta` → M-14 报 block。
- **T-24** `STATE.md` 超过 12KB → 重建时按节截断（速记优先丢），并记 warn，不影响装配。
- **T-25** 同一章 V4 跑两次 → `chapter_state` 是 UPSERT（`ON CONFLICT ... DO UPDATE`），不产生重复行。

## 7. F-06 双时间线

### 7.1 现状缺陷

没有任何机制区分「故事世界的真相」与「角色/读者目前知道什么」。这是长篇最隐蔽的硬伤来源：

- 角色说出他不可能知道的事（读者会立刻察觉，比错别字致命）
- 伏笔提前泄底（本该第 80 章揭的，第 20 章角色就知道）
- 作者写了两条互斥的真相版本（第 30 章说 A 杀了 B，第 60 章说 B 活着）

### 7.2 数据契约

`books/<书名>/TIMELINE.md`（人读 + 机解析）：

```markdown
# 时间线

## 一、作者真相（故事世界实际发生）

| 编号 | 章 | 事件 | 涉及角色 | 读者已知 | 知情角色 |
|---|---|---|---|---|---|
| T-001 | 1 | 林寒父母死于货柜爆炸 | 林寒 | 是 | 林寒,苏婉寒 |
| T-002 | 3 | 苏婉寒是幕后主使 | 苏婉寒 | 否 | 苏婉寒 |

## 二、读者已知（按章释放）

| 章 | 本章向读者释放的真相 |
|---|---|
| 1 | T-001 |
```

字段约束：
- `编号` 全局唯一，格式 `T-\d{3}`
- `章` 首次发生的章号
- `读者已知` ∈ {是, 否}
- `知情角色` 逗号分隔，必须是 `characters/` 里存在的名字（否则 M-16 报错）

### 7.3 生成与维护

- **不由 LLM 自由生成**：V4 只产出候选（`timeline_candidates: [{event, characters, reader_known}]`），写入 `conflicts` 队列类型 `timeline_candidate`，**人工确认后**才落 `TIMELINE.md`。
- 理由：时间线是一本书的骨架真相，自动写入会污染证据链（同 `M-04 敏感词禁止自动改写` 的道理）。

### 7.4 校验

| 规则 | 判据 | 级别 |
|---|---|---|
| M-16 时间线格式 | 编号唯一、章号合法、`读者已知` 枚举合法、`知情角色` 存在 | block（格式错） |
| M-17 悬空引用 | 正文/细纲提到 `T-xxx` 但表里无此编号 | warn |
| S-01 泄底（语义） | 本章出场角色说了 `读者已知=否` 且该角色不在 `知情角色` 的事实 | 由 V1 审校判 blocking |

M-16/M-17 是规则，S-01 是语义（必须 LLM）。V1 提示词新增变量 `时间线约束`，只注入本章涉及角色的知情范围（≤2000 字），不注入全表。

### 7.5 装配

不新增槽位。`bible_core` 槽尾部追加一段（≤800 字）：

```
【时间线约束】本章出场角色 T-002 未知情（读者亦未知），不得让其提及或指向该事件。
```

只注入**本章出场角色**的禁区，不是全表。

### 7.6 验收

- **T-26** `TIMELINE.md` 编号重复 → M-16 block，报具体行号。
- **T-27** `知情角色` 写了不存在的角色 → M-16 block。
- **T-28** V4 产出 `timeline_candidates` → 进 conflicts 队列，`TIMELINE.md` **不变**（未确认不得落盘）。
- **T-29** 装配预览里 `bible_core` 含「时间线约束」段，且只含本章出场角色的条目。

## 8. F-07 外部书稿挂载

### 8.1 现状缺陷

`books.book_dir(name)` 固定为 `books/<name>/`（`ainovel/books.py`），`create_book()` 强制 `mkdir` 新目录。用户 `D:\1-work` 下已有多个写作项目的书稿目录，**无法接管**，只能复制进来。

### 8.2 目标

能把任意已存在的书稿目录挂到书架，原地接管（不搬迁、不复制），缺失结构按需补齐且不覆盖已有文件。

### 8.3 数据契约

`books` 表已有 `path` 字段（`db.py:55-60`），本次启用为**权威路径**：

```sql
-- 已有，无需变更；新增约束由应用层保证
path TEXT NOT NULL   -- 绝对路径；内置书 = <project>/books/<name>，外挂书 = 任意绝对路径
```

`config.json` 新增字段：

```json
{
  "external": true,
  "attached_at": "2026-10-26T20:00:00",
  "original_layout": "novel-engine"   // 或 oh-story / flat-txt / unknown
}
```

### 8.4 接口

```
POST /api/books/attach
body: { name, path, scaffold: true|false }
→ { ok, name, path, detected: {layout, chapters: n, has_bible: bool, ...},
    scaffolded: ["STORY_BIBLE.md", "OUTLINE.md", ...] }
→ 409 当 name 已存在
→ 400 当 path 不存在 / 不是目录 / 无任何 .md 或 .txt

POST /api/books/{book}/detach
→ 仅从书架移除记录，不删文件（默认）；body {delete_files: true} 才删（需二次确认）
```

**安全约束**（重要，防误删用户资料）：

1. 拒绝挂载盘符根目录、用户主目录、`D:\1-work` 本身（黑名单 + 层级检查：路径必须至少有 2 层深度）。**这条是硬拦，不允许通过参数绕过。**
2. `scaffold` 只创建缺失文件，**已存在文件一个字节都不动**。
3. `detach` 默认不删文件。
4. 挂载前写 `data/.attach-backup/<name>-<ts>.json` 记录原 path 与文件清单，便于回退。

### 8.5 结构探测

按优先级识别已有结构：

| layout | 判定依据 | 映射 |
|---|---|---|
| `native` | 有 `config.json` + `chapters/` | 直接可用 |
| `novel-engine` | 有 `.soloent/` 或 `book.json` | 映射 `chapters/*.md` → 章节；`canon.md` → Bible 候选 |
| `oh-story` | 有 `大纲/` + `正文/` + `追踪/` | 映射需 F-08 支持 |
| `flat-txt` | 只有若干 `.txt` | 走 F-08 导入 |
| `unknown` | 其他 | 只挂载，不做映射，提示手工整理 |

`detected` 字段必须如实报告「没识别到的东西」，例如 `has_bible: false` —— 不允许把缺失当默认存在。

### 8.6 验收

- **T-31** 挂载一个只有 txt 的目录 → `layout=flat-txt`，提示走导入。

## 9. F-08 导入现存 txt

### 9.1 现状缺陷

无导入能力。用户大量成稿是裸 txt（各平台下载/自己堆的），系统一口吃不到，只能从第 1 章重新生成。

### 9.2 目标

把一个 txt 变成可继续写作的工程：切章、建大纲占位、可选补记忆卡。

### 9.3 两段式：预演 → 确认

**绝不一步写入**（切章规则错了会毁掉整份稿）。

```
POST /api/books/{book}/import/novel/preview
body: { file_path } 或 multipart 上传
→ {
    encoding: "gb18030",
    total_chars: 812340,
    chapters: [{no: 1, title: "第1章 夜雨", chars: 2680, start_line: 3}],
    warnings: [
      {kind: "gap", detail: "缺第 7 章"},
      {kind: "short", detail: "第 12 章仅 320 字"},
      {kind: "duplicate_title", detail: "第 5、18 章标题相同"}
    ],
    guessed_regex: "第[0-9一二三四五六七八九十百千]+章"
  }

POST /api/books/{book}/import/novel/commit
body: { file_path, regex, encoding, mode: "finalized"|"draft", rebuild_memory: false }
→ { imported: n, skipped: n, issues: [...] }
```

`warnings` 非空时 `commit` 必须带 `confirm_warnings: true`，否则 409。

### 9.4 切章规则

按优先级尝试正则（命中率最高者作默认值，但**由用户在预演页确认**）：

```
1. ^第[0-9零一二三四五六七八九十百千]+[章节回]  .*
2. ^[0-9]{1,4}[、.]\s*\S+
3. ^Chapter\s+\d+
4. ^【第.+?章】
```

编码探测顺序：`utf-8-sig` → `utf-8` → `gb18030` → `utf-16`；全部失败则报 `unparsed`，**不猜**。

### 9.5 落盘与状态

- 正文写入 `chapters/NNN_正文.md`（frontmatter：`chapter_no / title / word_count / imported: true / source_fingerprint`）
- **不写细纲**（历史章没有细纲，不伪造）。`OUTLINE.md` 追加占位行：「第 N 章（导入，无细纲）」
- 状态：
  - `mode=finalized` → `status='finalized'`（历史章已发布，语义正确），`imported=1`
  - `mode=draft` → `status='human_review'`（待人工确认），`imported=1`
- `rebuild_memory=true` → 逐章串行跑 V4（**章节多时极慢，默认 false**，UI 明示"将调用 N 次模型"）

### 9.6 断点续跑

导入 300 章中途崩溃不能从头再来：

- `data/import_jobs/<book>-<ts>.json` 记 `{file_fingerprint, regex, done: [no...]}`
- `commit` 前检查同名未完成 job，有则续跑
- 每章写完立即更新 job 文件（原子写）

### 9.7 验收

- **T-35** 导入 12 章 txt → 生成 12 个 `chapters/*_正文.md`，`list_chapters` 返回 1..12。
- **T-36** 预演阶段不产生任何文件（对比导入前后目录快照）。
- **T-37** 缺章（缺第 7 章）→ `warnings` 含 `gap`，未带 `confirm_warnings` 时 `commit` 返回 409。
- **T-38** GB18030 编码 txt → 正确解码，无乱码（抽样断言首章前 20 字）。
- **T-39** 导入中途 kill → 重跑 `commit` 从 `done` 之后继续，不重复写已有章。
- **T-40** `mode=finalized` 且 `rebuild_memory=false` → `memory-card/pending` 列出全部导入章（因为无卡），但这不算错误，UI 区分"导入待补"。

## 10. F-09 草稿恢复

### 10.1 现状缺陷

半成品落盘**已经实现**，但只写不读：

- `pipeline.py:420` `DRAFT_FLUSH_CHARS = 400`，`_draft_cb()` 每累积约 400 字写一次 `<no>_正文.draft.md`
- 已接到 `_generate_prose_inner`（`pipeline.py:457`）
- **`api.py` 中没有任何读取、采用、丢弃草稿的入口**

后果：第 12 章正文生成 93 秒，若在第 80 秒断网，已生成的约 2200 字全部躺在 `.draft.md` 里，用户只能点「重写」从头再来——白烧一次 token。这是"流程正确"上的窟窿：**系统已经付出了成本，却没有把成果交回给人**。

### 10.2 目标

草稿可查看、可采纳、可丢弃。采纳后的正文与正常生成同等对待（必须过机检）。

### 10.3 接口

```
GET  /api/books/{book}/chapters/{no}/draft
→ { exists: bool, chars: n, generated_at, preview: 前200字, stale: bool }
→ exists=false 时其余字段为 null（不是 404，前端好处理）

POST /api/books/{book}/chapters/{no}/draft/adopt
body: { force: false }
→ { ok: true, chars: n, status: "mech_check" }
→ 404 当无草稿
→ 409 当 status 不是 error / generating
→ 422 当 chars < 500 且 force=false（这么大的稿大概率只是开头，采纳要显式确认）

POST /api/books/{book}/chapters/{no}/draft/discard
→ { ok: true }
```

### 10.4 状态机变更

新增一条救援出边（`statemachine.py`）：

```python
("error", "adopt_draft"): "mech_check",
```

理由：`error` 现在只能 `retry` 回到 `generating` 重新生成，无法把已有半成品推向下一关。采纳草稿的语义是「这份正文我认为可以作为本章」，与 `generating --complete--> mech_check` 等价，因此直接进机检。**只进更严的关卡，不放宽任何门禁。**

`generating` 状态下也允许 adopt（用户主动中断后）——需先 `abort` 到 `outline_locked`，再走不了。因此 `generating` 状态调用时先 `transition("fail")` 落 `error`，再 `adopt_draft`。

### 10.5 采纳流程

```
1. 读 draft.md，去 frontmatter 残留，trim 首尾空行
2. 字数校验（<500 需 force）
3. 写正式正文 chapters/<no>_正文.md（frontmatter: status=draft, word_count, version 不变）
4. generation_log 记一条 stage='draft_adopt'（便于日后统计"多少章靠草稿救回"）
5. 删除 draft.md
6. transition("adopt_draft") → mech_check
7. 机检照常跑（含 F-01 指纹写入）
```

**不得跳过机检**：草稿是半成品，更可能字数不足或残缺，必须让 M-01 判定。

### 10.6 过期判定

草稿 mtime 早于正文 mtime 时视为过期（正文后来手动改过），`GET draft` 返回 `stale=true`，`adopt` 需 `force`。避免用 10 天前的废稿覆盖现在的正文。

### 10.7 验收

- **T-41** 生成中途注入异常 → `_正文.draft.md` 存在且字数 > 0，`GET draft` 返回 `exists=true`。
- **T-42** `adopt` → 正文写入、`draft.md` 被删除、状态为 `mech_check`、`generation_log` 含 `stage=draft_adopt`。
- **T-43** 无草稿时 `adopt` → 404，正文文件不变。
- **T-44** 草稿 320 字 → `adopt` 返回 422；带 `force=true` 则成功，且机检立刻报 M-01 字数不足（证明没有绕过检查）。
- **T-45** 草稿 mtime 早于正文 → `stale=true`，不带 `force` 拒绝。

## 13. 迁移顺序

依赖关系决定顺序，不能并行乱做：

```
F-01（假绿防护）          无依赖，先做
  ↓
F-03（词表/规则参数）      被 F-02 依赖
  ↓
F-02（检测器）            依赖 F-03 的 yaml 与词表分级
  ↓
F-05（状态快照）          被 F-04 依赖（回滚基线）
  ↓
F-04（记忆卡补做）        依赖 F-05
  ↓
F-06（双时间线）          依赖 F-05 的 knowledge 字段
  ↓
F-07（挂载）              独立，可与上并行
  ↓
F-08（导入）              依赖 F-07（需要先能挂目录）
  ↓
F-09（草稿恢复）          独立，最小工作量，可在任意阶段插入
```

**每步独立可验收、可提交**，不允许"八项一起改完再测"。

## 14. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 词表扩容过猛导致旧章大量报错 | 第 1-12 章可能新增几十条 block | 扩容后先跑**只报不拦**模式，人工看一遍再加进 block 级 |

| 挂载外部目录误删用户资料 | **不可逆** | §8.4 的四条安全约束为硬拦；`detach` 默认不删；挂载前备份清单 |
| 导入切章误判 | 毁掉整份稿 | 两段式预演 + 断点续跑 + 预演不写盘 |
| 新检查器误杀（护栏类） | 合法修改被拒（P1 已发生两次） | block 级只用于**结构性硬伤**；语义类一律 advisory；阈值外置可调 |
